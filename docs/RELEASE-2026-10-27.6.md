# Release 2026-10-27.6 — the dashboard in a container

The dashboard can now run in a container, with the settings mounted in from
the host and one command to update it.

## What it does

```
  Pi screen(s) ──HTTP──►  the container  ──HTTPS──►  FoxESS / Octopus
                         │  reads
                         ▼
                   ./config/config.json
```

One container does all the work: it holds the FoxESS session, the Open API
key and the Octopus credentials, and it serves the page to every screen. The
Pi screens are dumb terminals — they need a browser and an address, nothing
else.

```bash
mkdir -p config && cp config.example.json config/config.json
chmod 600 config/config.json

docker compose up -d --build
```

## The settings file is never in the image

This is the rule the whole design hangs on.

The settings file holds the FoxESS password, the Open API key and the Octopus
API key in plain text. If it were copied into the image, it would sit in a
layer forever, and a rebuild would be a chance to lose it.

So the **whole `./config` directory** is mounted into the container instead.
The directory, not the file, because the dashboard writes the half-hourly
history next to the settings and replaces the settings file atomically —
both of which need a real directory. `.dockerignore` keeps it out of the
build context as well, and `.gitignore` keeps it out of the repository.

## The image

The dashboard is written against the Python standard library only, so there
is nothing to install and nothing to compile: the image is the official
Python one, plus the timezone database.

**tzdata is not optional.** The dashboard asks the OS for its timezone by
name — `Europe/London` and friends — and the slim images do not ship the
timezone database. Without it `ZoneInfo` raises `ZoneInfoNotFoundError`, and
the clock and the solar forecast go down with it.

The container does not run as root. It runs as uid 1000, which is the first
ordinary user on Raspberry Pi OS, so the settings file usually already
belongs to the right person. `docker-compose.yml` can override it with
`FOXESS_UID` and `FOXESS_GID`.

`/healthz` answers `{"ok": true}`, so Docker knows when the container is up —
and so the update script knows when the new one is.

The image builds for `linux/amd64`, `linux/arm64` (Pi 4, Pi 5) and
`linux/arm/v7` (Pi 3).

## Updating

```bash
./update.sh
```

1. **pull** the newest code (`git pull --ff-only`)
2. **build** a new image from it
3. **tag** the image that is running now as `foxess-dashboard:previous`
4. **replace** the container with the new one
5. **wait** for `/healthz` to answer

If the new container does not come up within two minutes, the old image goes
back and the log of what went wrong is printed. **A failed build never
touches the container that is running**, so a bad update costs nothing but a
rebuild.

The script says so, and stops, if the repository has no git remote — there
is nowhere to pull from, and a mystifying git error helps nobody.

It also checks, before it replaces anything, that the container can actually
write to the settings directory. That is the most common first-run failure,
and it is caught before the swap rather than after.

## The screens

```bash
python3 display/pi_kiosk.py --url http://<host-ip>:8765 --no-server
```

`--no-server` says "the server is somewhere else" — which is the whole point
here: the container serves the page, and the Pi just shows it.

## The catch

**The dashboard has no authentication.** Anything that can reach the port can
read the page, change the settings, and ask the server for the settings in
plain text (`/api/settings/export` returns the password and the API keys).

That is a deliberate choice for a private LAN. It means the port must stay on
the LAN, and the settings file — the crown jewels — must stay `0600` and out
of git.
