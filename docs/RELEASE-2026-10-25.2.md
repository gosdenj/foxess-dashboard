# Build 2026-10-25.2 — the Octopus meter readings

## The problem

The Octopus panel showed the import and export **rates**, but never the
**meter readings** (how much you imported, exported, and what it cost).
The rates are public, so they worked without an API key; the readings need
one, and the lookup that finds your meter was never being called.

## What was wrong

1. **The lookup was never called.** The worker stored the account number and
   then went straight to the rates. Nothing ever asked Octopus *which meter*
   the account number refers to.
2. **The GraphQL query used fields that do not exist.** The account's meter
   point lives under `electricityAgreements → meterPoint`, not under
   `supplyPoint` / `product`.
3. **The client had no `export_meter_serial`.** Fetching the export meter
   raised an `AttributeError`, which was caught by the broad handler and
   replaced the whole panel — including the import figures — with an error.
4. **Failures were silent.** The error went into the state, but nothing said
   why, and the next attempt was five minutes away.

## What changed

- The account is now looked up **first**, with two routes:
  - **REST** `GET /v1/accounts/{account_number}/` — tried first, because it
    works with an ordinary API key. The response is walked rather than
    assumed, so it survives the layout changing.
  - **GraphQL** — kept as a fallback.
  If both fail, both errors are reported.
- `export_meter_serial` exists on the client and is saved in the settings.
- Errors are **printed to the server console** and shown on the panel, and
  the next attempt is **30 seconds** later rather than five minutes.
- The panel says which of these it is:
  - *"The rates are public - add an API key for your meter readings"*
  - *"No meter readings yet - check the API key and account number"*
  - the exact error, when there is one.
- **New: a "Test the connection" button** on the settings page, next to the
  Octopus section. It tries the credentials and tells you what it found,
  before anything is saved — so you do not have to wait for the server to
  notice.

## How to use it

1. Open the settings page and go to **Octopus Energy**.
2. Paste your **API key** and your **account number** (`A-…`).
   The account number is enough — the MPAN and the meter serial are found
   for you.
3. Press **Test the connection**.

   ```
   OK - found 1234567890123 / 11ABCDEFG - 48 readings, 12.34 kWh
   ```

   or, if something is wrong, the exact reason:

   ```
   rest: HTTP 401: {"detail":"Invalid API key."}; graphql: Value of
   'Authorization' header is not a valid credential.
   ```
4. Save. The Usage slide picks the readings up within half a minute.

If you already know the MPAN and the meter serial, you can type them in
instead — anything you type wins over the lookup.

## The layout check

`layout_check.py` used to measure whatever the demo happened to generate,
so it only caught the layouts that happened to have short numbers. It now
measures the **worst case** — the longest values the display ever shows
(`12.34 kW`, `9999.99 kWh`, `99.99p`) — and holds every slide to it at
every size. It also takes `--sizes` and `--diagrams`, so a single
viewport can be checked on its own:

```
python3 layout_check.py 8770 --sizes laptop --diagrams rings
```

# Build 2026-10-25.3 — the query Octopus rejected

## The problem

```
HTTP 400: {"group_by":["half-hour is not a valid value for group_by"]}
```

The key was fine; the request was not. Octopus's own schema lists the
accepted `group_by` values as **`hour`, `day`, `week`, `month`, `quarter`**
— there is no `half-hour`, because half-hourly is what the endpoint
returns *by default*. Passing `group_by=half-hour` asks for something
that does not exist.

The ordering was wrong too: `order_by=asc` is not a value Octopus knows
either. The two are `period` (oldest first) and `-period` (newest first).

## What changed

- `group_by` is no longer sent — half-hourly is the default.
- `order_by=period` — oldest first.
- The readings are sorted by their start time in any case, so the order
  never depends on the API.
- **"Today" now means the local day.** The window started at
  *yesterday's* midnight — `now - 1 day` with the hour zeroed — so it
  ran for over 24 hours and mixed two days together. It now starts at
  local midnight, converted to UTC, so it is an hour out for half the
  year in the right way. The same fix applies to the test button.

## The request it makes now

```
/v1/electricity-meter-points/<mpan>/meters/<serial>/consumption/
  ?period_from=2026-10-24T23:00:00Z   <- local midnight, in UTC
  &period_to=2026-10-25T19:13:06Z
  &order_by=period
  &page_size=250
```

healthy. But the half-hourly history — which is what fills the usage

# Build 2026-10-25.7 — the inverter's own daily totals

You asked the right question: the Today panel was being filled from the
locally recorded history, which starts from nothing every time the
dashboard restarts. The inverter already knows its own daily totals.

## The production report

The Open API has two more endpoints that were not being used:

- `POST /op/v0/device/report/query` — the production report. With
  `dimension: "month"` it gives one value per day of that month; with
  `dimension: "day"` it gives one value per hour of that day.
- `POST /op/v0/device/generation` — today's, this month's and the
  lifetime generation.

The monthly report is used for the totals, not the daily one, because
the daily report is known to be a little wrong at the edges of the day
— the value for a day comes from the hour-based register and has not
settled yet. The community's own advice is to take the day from the
month.

The response is positional:

```json
{"result": [{"variable": "generation", "values": [ ...one per day... ]}]}
```

so today's figure is the value at the index of today's date.

## What the Today panel shows now

| Figure | From |
|---|---|
| Solar | `generation` |
| House | `loads` |
| Battery | `dischargeEnergyToTal` |
| Grid | `gridConsumption` |
| Export | `feedin` |

These come from the inverter, so they are right even when the dashboard
has only just started. The locally recorded history is still used for
the chart, because a chart needs half-hourly detail that the report
does not have — and if the history is empty, the inverter's **hourly**
report draws the chart instead, so the usage slide is never blank.

The report is fetched on the same five-minute poll as the rest of the
Open API data, and a failure there does not affect the live figures.

## Where the Octopus readings stop

The probe now says when the readings run from and to, and what the
server thinks the time is:

```
2000000000001 21L0000001 (meter) 7 days: 245 readings, 79.65 kWh,

so it is obvious whether the readings are stale or the window is wrong.

# Build 2026-10-25.10 — the Octopus worker was being killed

## What was happening

The Import, Export and Cost figures only appeared after pressing
**Test the connection**, and stayed empty otherwise.

Saving the settings calls `apply_settings`, which restarts the Open API
poller by setting `self.stop` and making a new event. But `self.stop`
was the controller's *shutdown* event — and the Octopus worker was
given that same event to watch. So **saving the settings stopped the
Octopus worker for good**. It kept whatever it last had and never
updated again.

The Test connection button was unaffected, because it does its work in
the request thread rather than the worker — which is exactly why it
looked like the button was what made the data appear.

## The fixes

- The Open API poller has its own stop event now. `self.stop` means
  "shut everything down" and nothing else.
- The Octopus worker gets a wake event instead: a settings change
  makes it refresh straight away rather than at its next five-minute
  round.
- The Octopus worker survives anything that goes wrong in a poll,
  rather than dying quietly and freezing the panel.

## Two more bugs in the same function

- The saved settings are a **flat** dict of paths (`foxess.user`), but
  the code looked for `saved["foxess"]["user"]` — so it always thought
  the credentials had changed, and restarted the live feed and the
  poller on **every** save.
- A blank or masked field means "keep what is stored", but the code
  compared `"********"` against the real password, so a masked secret
  counted as a change too.

Both are fixed, with tests.

## And the first pass no longer waits for nothing

The worker waits up to a minute for the inverter's daily report before
pricing the meter — but only when there is an Open API key to fetch it
with. Without one it used to sit and wait for a report that was never
coming.

# Build 2026-10-25.11 — the credentials were never saved

## What was happening

The Import, Export and Cost figures stayed empty, and pressing **Test
the connection** did not help — although it found the meter perfectly
well.

The reason: **the test button used the form, and the worker reads the
settings file.** The account number had been typed into the form and
tested, but never saved, so the worker had no account number to look

## The fixes

- **The test button now saves what it tested.** The button is called
  *Save and test*, and it writes the Octopus settings that actually
  changed — a blank or masked field still means "keep what is stored",
  so the masked key is never written back.
- The settings save wakes the Octopus worker, so the panel updates
  within a second or two instead of at the next five-minute round.
- The whole worker body is now inside a guard, so nothing that happens
  in a poll — a failed lookup, a full disk, anything — can kill it and
  leave the panel quietly frozen.

## Worth knowing

`resolve_meter` saves the MPAN and the meter serial once it has found
them, so after the first successful test the account number is only
needed once.

# Build 2026-10-25.14 — the export MPAN

## Why it was empty

A Flux meter has two registers — import and export — and Octopus
registers them as **two meter points**, sharing one physical meter:

```
2000000000001   the import
2000000000002   the export
```

The account response lists both, with the same meter serial, and does
not always say which is which. My code took the first as the import
and never found the export, so the export MPAN was never filled in.

The meter point itself knows: an export meter point carries the
`import_mpan` it belongs to. So each meter point is now asked directly,
and that is what tells the two apart — no guessing from the readings
or the MPAN's digits.

## It will fill itself in

The worker only looked the meter up when the meter serial was missing,
so it would never have gone back for the export. It now looks up until
both halves are found, and the test button does the same.

Your account, from the mock of its exact shape:

```

# Build 2026-10-25.18 — checking the daily figures against the hours

## Two ways of counting the same day

The daily figures come from the inverter's monthly report, one value
per day. The same inverter also reports **an hourly breakdown** for the
day, and the hours that have gone by should add up to the day in the
monthly register.

Both are now fetched and compared, and the difference is shown:

```
daily report: pv 2.30, house 1.10, grid_in 0.90, ...
  pv: month 2.30 vs hours 1.00 (difference +1.30)
  house: month 1.10 vs hours 1.00 (difference +0.10)
  balance: +2.00 kWh
```

So if the monthly register and the hours disagree, it is now visible
rather than a matter of opinion. The day is taken from the monthly
register - the hours are only just settling, so they are the one that
is more likely to be short.

## The balance

The sun, the battery and the grid brought in, less the house, the
battery and the grid took out, should be near zero - what is left is
the battery's own losses. A balance that is far from zero means one of
the figures is wrong or from a different window.

```
in:  pv + batt_out + grid_in
out: house + batt_in + grid_out
```

The Detected table on the settings page shows both the comparison and
the balance, and refreshes with everything else.

# Build 2026-10-25.19 — the solar figure was the wrong number

## There are two solar numbers, and I had the wrong one

The production report has both:

- `generation` — the **inverter's AC output**
- `PVEnergyTotal` — the **PV yield**, which is what the Fox app shows

For a hybrid inverter those are not the same thing: the inverter's
output includes what the battery sent out, while the PV yield is only
what the roof made. The dashboard was showing the inverter's output as
"solar generated" — three and a half kWh where the app said two
tenths.

The solar figure now comes from `PVEnergyTotal`.

## The app's own method

`PVEnergyTotal` is a running total, not a daily figure, so today's
yield is the difference between the end of today and the end of
yesterday — which is exactly how the app works it out, and it does not
need the dashboard to have been running since midnight.

## Three opinions, side by side

```
pv yield today: 0.20 kWh (the counter is at 1016.20)
pv from the live feed: 0.24 kWh (difference -0.04)
```

- the **PV yield** from the running counter — what the app shows
- the **hours** of the inverter's own hourly report, added up
- the **live feed's own integration** of the solar power, which is what
  the usage chart is drawn from

The last one only covers from whenever the dashboard started, so it is
a check rather than the figure.
