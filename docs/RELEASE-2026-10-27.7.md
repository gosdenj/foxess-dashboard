# Release 2026-10-27.7 — the dashboard learns to be a Portainer stack

Portainer runs the dashboard as a stack: a compose file it deploys, and
keeps up to date for you.

## The catch that shapes it

**Portainer redeploys a stack without rebuilding it.** Under the hood it
runs `docker-compose up -d` — with no `--build`. So a redeploy updates the
*compose file* but keeps the *image it already has*, and a new commit
would never reach the running container.

That is not a detail to work around quietly; it decides the shape of
everything else.

## So the image comes from the registry

```
   push to main
        │
        ▼
   the GitHub workflow builds the image ──► ghcr.io/…/foxess-dashboard:latest
        │
        ▼
   Portainer notices the repository has changed, re-pulls the image
        │
        ▼
   the new version is running
```

The workflow is `.github/workflows/docker.yml`, and it signs in with the
workflow's own token — there is no secret to set up. It builds for all
three architectures: a hosted Intel server, an Apple Silicon Mac, a
Raspberry Pi 4 or 5, and a Raspberry Pi 3.

The image is tagged `latest` and with the commit it came from.

## The settings live in a volume

A named Docker volume, `foxess-config`, mounted at `/config` — rather than
a folder on the host, for three reasons:

- it is the **same** wherever the container runs, with no path to get wrong
- it **survives a redeploy** — a redeploy replaces the container, not the
  volume
- it does not depend on the host and the container sharing a filesystem,
  which they do not if Portainer is a container with Docker Desktop
  underneath it

The volume takes its ownership from the image, where `/config` belongs to
uid 1000 — the uid the container runs as. So the dashboard can write to it
without anybody having to `chown` anything.

## What Portainer does not do

**There is no rollback.** That is the one thing Portainer does not do that
`update.sh` does. If a new version breaks the dashboard, the way back is
to move `main` back to the last good commit and let Portainer redeploy.

The `update.sh` path is still there, and still does the whole job — pull,
build, swap, wait for it to answer, put the old one back if it does not.
The two are alternatives: Portainer owns the stack, or the host's compose
does.

## Testing

- 461 tests (was 445): 16 more for the Portainer stack — that the image
  comes from the registry and is not built locally, that the settings are
  in a volume with a fixed name, that the stack's compose file agrees with
  the command-line one about the port, the environment and the container,
  and that the workflow publishes on a push with only the permissions it
  needs.
- The image was built for all three architectures: `linux/amd64`,
  `linux/arm64` and `linux/arm/v7`. The 32-bit one was run as well, and
  the timezone database is in it.
- Both compose files were checked with `docker compose config`, and the
  named volume renders as a volume rather than a host path.
- The tests were mutation-tested: changing the workflow's permissions,
  adding a `build:` section to the Portainer file, or moving the settings
  back to a host path each fail the suite.
