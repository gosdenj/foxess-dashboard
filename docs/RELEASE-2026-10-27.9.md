# Release 2026-10-27.9 — the workflow checks whether it has anything to do

The update pipeline had a quiet flaw in it, and this is the second half of
the fix.

## The flaw

**A push made with an OAuth token does not start a workflow at all.**

The token in this machine's keychain is an OAuth token (`gho_…`), and a
push made with one leaves the image for that commit unbuilt. The
dashboard then sits on the old version until somebody happens to commit
again — which, for a dashboard, might be weeks. Nothing says so: the
push succeeds, the repository moves, and the image simply never appears.

A classic personal access token does start the workflow, and the pushes
from here on use one. But a pipeline that depends on *how* somebody
happens to push is a pipeline waiting to go quiet, so the workflow does
not depend on it any more.

## What the workflow does now

It asks first: **has the image for this commit already been published?**

The image is tagged with the commit it was built from — `sha-18e7abe…` —
so the registry can be asked directly. If the answer is yes, the run
does nothing at all: no build, no push, no commit.

And there is a **safety net**: the workflow also runs every four hours,
which catches the push that did not trigger it. A run that finds nothing
to do costs a few seconds and builds nothing.

A commit that is only the signal — the empty one made at the end — carries
no code of its own, so the image for it is the image for the commit
before it, and there is nothing to do there either.

## What Portainer sees

```
   push to main
        │
        ▼
   the workflow builds the image and pushes it to the registry
        │
        ▼
   the workflow commits "publish <sha> [skip ci]"    ← the signal
        │
        ▼
   Portainer polls, sees the change, re-pulls the image, restarts
        │
        ▼
   the new version is running
```

Portainer polls every five minutes. The order matters: the signal comes
*after* the image is published, so the redeploy never finds a stale
image. And if it happens to poll in the window before the image is ready,
it redeploys once more when the signal arrives, so the pipeline heals
itself either way.

## Testing

- 464 tests (was 462): two more for the workflow — that it asks the
  registry whether the image is already there, and that the safety net
  is there at all.
- The whole loop was watched working: the signal commit appeared on the
  repository, Portainer noticed within five minutes, re-pulled the image
  and restarted the container, and the dashboard came back on the new
  build.
