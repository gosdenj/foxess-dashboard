# Release 2026-10-27.8 — the image is published before Portainer is told

The update pipeline had a quiet flaw in it, and this fixes it.

## The flaw

Portainer notices that the **repository** has changed and redeploys the
stack — re-pulling the image as it does. It had no idea whether the image
for that commit had been built yet.

So it could poll in the window between the push and the image being
ready, find the old image, and deploy it. And then it had no reason to
look again: the repository had not changed, so there was nothing to
redeploy. The new code would have sat there, published but not running,
until somebody happened to commit again — possibly weeks later.

## The fix

The workflow now makes one small commit **after** the image has been
pushed:

```
   push to main
        │
        ▼
   the workflow builds the image and pushes it to the registry
        │
        ▼
   the workflow commits "publish <sha> [skip ci]"    ← this is the signal
        │
        ▼
   Portainer polls, sees the change, re-pulls the image, restarts
        │
        ▼
   the new version is running
```

`[skip ci]` keeps that commit from starting the workflow all over again.
It is an empty commit — nothing in it but the message.

If Portainer does happen to poll in the window before the image is
ready, it redeploys the old image and then redeploys again when the
signal commit arrives, so the pipeline heals itself either way.

## Testing

- 462 tests (was 461): one more for the workflow, checking that the signal
  commit comes **after** the build and that it says `[skip ci]`.
- The test was mutation-tested: moving the signal commit before the build
  fails the suite.
